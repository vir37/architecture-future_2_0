### Проблемные места текущей архитектуры.

1. **Централизованное хранилище данных**. Уже в настоящий момент хранит в себе огромное количество информации и страдает низкой производительностью. А надо еще учитывать планы по открытию новых направлений.
2. **Предназначено для хранения структурированных данных**. В качестве хранилища используется БД, которая лучше всего подходит для хранения структурированных данных. 
Это означает, что поступающая извне информация должна быть предварительно трансформирована. А это несет в себе как дополнительные накладные расходы, так и потерю части информации, которая могла бы быть полезной.
Для машинного обучения как раз очень важны неструктурированные данные.
3. **Отсутствуют инструменты тегирования данных**. Поступающие в хранилище данные могут содержать конфиденциальную информацию. За отсутствием инструментария для автоматической пометки важной информации
задача выявления таковой ложится на плечи персонала, обслуживающего DWH. Каждый новый источник данных должен быть проанализирован. Тут заложена опасность пропустить данные, которые должны обрабатываться в соответствие с требованиями законодательства.
4. **Отсутствуют механизмы отслеживания жизненного цикла данных**. Data Lineage не реализован. А значит практически невозможно проводить аудит работы с данными. Кроме того сложно организовать автоматический вывод из эксплуатации данных, которые устарели и потеряли ценность.
В результате хранилище необоснованно разрастается.
5. **Сложно управлять правами доступа к данным**. Когда все данные сосредоточены в одном хранилище, корректно раздать права пользователям для доступа только к тем данным, которые им необходимы, становится очень сложной задачей. Есть большие риски дать лишних прав.
6. **Нагрузка на команду, которая управляет хранилищем**. При существующем централизованном хранилище управлением им занимается одна команда. Причем нет разницы, какого рода данные поступают на хранение. Команда должна уметь правильно работать с этими данными, т.е. фактически знать бизнес-смысл любой информации.
Это очень сильно нагружает команду, и чревато потерей целостности, противоречивостью хранимой информации.


### Приоритезация решения указанных проблем по методу MoSCoW.
1. Must have:<br>
1.1. Решить проблему 3 (Отсутствуют тегов на данных). Некорректная работа с чувствительной информацией может нанести серьезный ущерб компании, как финансовый,  так и репутационный. 
2. Should have:<br>
2.1. Решить проблему 4 (Отсутствие механизма отслеживания жизненного цикла данных). При большом объеме данных внедрение Data Lineage повысит аудируемость системы.
2.2. Решить проблему 1 (Централизованное хранилище данных). Уже сейчас наблюдается деградация производительности. С этим надо что-то делать.
3. Could have:<br>
Проблемы 2,5,6 отнесены к этому приоритету. Проблемы должны уйти при решении проблемы 1 - переходе от централизованного хранилища к распределенному с использованием DataHub + Data Lakehouse. Поступающие в такое хранилище данные сразу же снабжаются метаданными, жизненный цикл их отслеживается. 
Data Lakehouse может эффективно хранить и управлять как структурированными данными, так и полуструктурированными и неструктурированными. DataHub позволяет снять нагрузку с централизованной команды и переложить её на реальных владельцев данных - команды, которые обладают экспертизой в продуцируемых ими данных. 
Кроме того, распределенное хранение данных (в границах доменов) позволяет более эффективно управлять правами доступа.
